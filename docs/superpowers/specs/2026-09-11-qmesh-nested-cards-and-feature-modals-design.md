## 0. 왜 지금 하는가

현재 카드는 FinAllQ·InsuQ·MaintQ를 **QMesh 카드 안의 불릿 3줄**로만 다룬다.

```html
<li><b>FinAllQ</b> · 은행·증권 통합 금융 비서 - … <span class="mono">:9001</span></li>
<li><b>InsuQ</b> · 실손 약관 RAG 에이전트 - … <span class="mono">:9002</span></li>
<li><b>MaintQ</b> · 제조 설비보전 에이전트 - … <span class="mono">:9003</span></li>
```

각각 7주 이상 단독 개발한 프로젝트인데 한 줄씩만 얻고 있다. 세 프로젝트의 분량이 많아
QMesh 본문에 풀어 쓰면 A2A 이야기가 묻히고, 별도 최상위 카드로 빼면 "QMesh가 이 셋을 잇는다"는
관계가 끊긴다. **중첩 드롭다운**이 둘 다 지킨다.

동시에 SpendQ 카드가 사실과 크게 어긋나 있다(§3-E).

## 2. 자산 정책 - 왜 이 레포에 담는가

### 실측한 레포 공개 상태 (2026-09-11, `gh repo list`)

| 레포 | 공개 | Pages |
|---|---|---|
| `key-manager` | public | ✅ `https://ttogle918.github.io/key-manager/` [built] |
| `QMesh` | public | ❌ 꺼짐 |
| `MaintQ` · `InsuQ` · `FinAllQ` · `SpendQ` | 🔒 **private** | ❌ |

### 결론: 외부 링크 방식은 성립하지 않는다

| 방식 | 판정 |
|---|---|
| `raw.githubusercontent.com` 핫링크 | ❌ private 레포는 토큰이 있어야 읽힌다. `<img src>`로는 깨진 이미지. public이어도 GitHub가 CDN 용도를 권장하지 않는다 |
| 소스 레포에 Pages 켜기 | ❌ private 레포 Pages는 유료 플랜이고, 켜도 그 사이트는 공개된다 - 소스를 여는 것과 같다 |
| **이 레포에 복사** | ✅ **채택** |

### 채택 근거

1. **선택적 공개가 목적과 일치한다.** 소스·시드·설계문서는 private에 남기고,
   **파일 단위로 고른 것만** 이 public 레포에 담는다. 레포를 여는 순간 잃는 통제권을 그대로 쥔다.
2. **포트폴리오는 자기완결이어야 한다.** 보는 중에 외부 링크가 죽으면 그게 곧 감점이다.
   레포 이름 변경·visibility 변경·Pages 재빌드 실패는 전부 손을 떠난 변수다.
3. **`qmesh/`가 이미 이 방식**이다 (QMesh는 public인데도 Pages를 안 쓰고 직접 호스팅).
4. 38MB → 약 47MB는 GitHub Pages 권장 한도(1GB)의 5% 미만.

### 공개 안전성

이 레포는 public이므로 **올린 자산은 곧 공개**다. 확인 결과:

| 프로젝트 | 데이터 성격 |
|---|---|
| MaintQ | 전부 목업 - 공개 매뉴얼(LS일렉트릭) + 생성 시드 |
| InsuQ | 시드 고객. 약관은 보험사 상품공시실 공개 PDF |
| FinAllQ | `demo-employee@finallq.example` 등 가짜 도메인 시드 계정 |
| QMesh | A2A GIF 3종은 **이미 이 레포에 공개돼 있다** (선례) |

> 실제 파일은 이관 직전에 목록으로 한 번 더 확인한다.

### 최적화

`ffmpeg`·`gifsicle`·`magick` 없음. **Pillow 12.3.0**으로 처리한다 -
폭 상한 + 프레임 솎기 + 팔레트 최적화. 원본은 각 프로젝트 레포에 그대로 남으므로

### A. QMesh (최상위)

| 블록 | 내용 | 근거 |
|---|---|---|
| 해결한 문제 | MCP는 자기 도구를 쓰는 층. 남의 조직 에이전트에 일을 맡길 때 필요한 신원 증명·사람 승인 대기·크로스도메인 추적을 다루지 못한다 | `04_8_QMesh` §1 |
| 계약 설계 ① | **신원을 actor(토큰) / subject(payload)로 분리** - 사업자번호는 공개정보라 payload 단독 식별은 폐기. 초안을 버리고 FinAllQ 쪽 조사 결론을 채택 | §3-① |
| 계약 설계 ② | **인증은 위임, 인가는 자원 보유자가 보유** - actor≠subject의 첫 실제 사례가 여기서 나왔다 | §3-② |
| 계약 설계 ③ | **`rejected`를 계약에 자리로** (CP-001) - 스킬 5종 중 4종이 `enum:["completed"]` 단일값이라 거부를 담을 자리가 없었다. **`rejected`는 HTTP 200** - 거부는 정상 동작이지 장애가 아니다 | §3-③ |
| 계약 설계 ④ | **근거 인용 형식을 정규식으로 고정** - `policy_part`가 빠지면 다른 파트의 같은 조 번호를 지어내도 환각 탐지를 통과한다 | §3-④ |
| 구현 | 어댑터 2종 974행 · `X-Request-Chain-Id`와 body 불일치 시 거부 · **404(없는 스킬)와 501(안 만든 스킬) 구분** · 상대 상태값 6종을 계약 3종으로 접되 계약 밖 값은 예외 | §4 |
| HITL | 자금이동 **3단 승인**(MaintQ 팀장 → MaintQ 재무 → FinAllQ 재무) · A2A 판정은 참고용(`Loan.status`는 `UNDER_REVIEW` 유지) · 담보가 풀려도 결정 문서는 `draft` | §5 |
| 성과 | 스키마 **13종** · Agent Card **3종** · 종단 검증 **5경로** · 테스트 **123건** · SSOT drift **0건** | §6 |
| 아직 안 된 것 | 오케스트레이터 `:9000` **미구현** - 지금 통신은 전부 P2P 직접 호출. MaintQ 수신은 **설계상 없음**(카드 `skills: []`) - 미착수가 아니라 하지 않기로 한 일 | §6 |

**모달 (2종)** - `assets/qmesh/`
- `request-settlement` - 상대 응답이 내 상태를 바꾸는 유일한 경로 (`BLOCKED` → `CONDITIONAL`)

### B. FinAllQ (하위) - **기능 먼저, 그 다음 "왜 LLM이 없는가"**

사용자 확정 순서. 기능 목록이 위, 기술 의사결정이 아래.

**기능 7종** (전부 모달 · `assets/finallq/` 스크린샷 보유 · 출처 `FinAllQ/docs/demo-walkthrough.md`)

| # | 기능 | 모달 핵심 | 화면 |
|---|---|---|---|
| 1 | 통합 대시보드 | 은행 계좌 + 증권 보유종목 합산. 규제 경고는 하드코딩 문구가 아니라 포트폴리오 비율을 임계값과 비교한 **실제 룰 판정** | 02 |
| 2 | 여신 심사 근거 카드 | 한도(사용률)·담보(LTV)·규칙 판정이 전부 실제 계산값. **심사 시점과 같은 판정 로직을 재사용** - 쓰기·읽기가 로직을 공유 | 03·04 |
| 3 | 여신 ↔ 이체 연결 | 원금·집행액·잔여 한도를 서버가 실시간 집계. `disbursable===true`일 때만 버튼 노출 - **판정은 서버가, 화면은 결과만** (프론트에서 복제하지 않는다) | 05·06 |
| 4 | 기업 이체 결재 | 신청자에게 승인 버튼이 **없다** - 요청자≠결재자 직무 분리(`ApprovalPolicy`). 결재함에 요청자의 1일 한도 사용액을 함께 표시 | 07·08 |
| 5 | **FDS 고위험 → 2FA 승격** | 결재(사람)를 통과해도 FDS가 **별도로 재평가**한다. 고위험이면 TOTP 2FA 없이는 완료되지 않는다 - 규칙(한도)→모델(FDS) **이중 방어** | 09 |
| 6 | 스미싱 탐지 | TF-IDF + LogisticRegression. 위험점수와 **위험 단어를 근거로** 제시. 이력은 JWT 주체로 서버가 확정(IDOR 방지) | 10·11 |
| 7 | AI 비서 - 정직한 실패 | 매칭 툴이 없으면 지어내지 않고 "범위 밖"이라 답하고 근거를 노출. 기능 호출 실패는 **배너로 그대로 알린다**(Fail-soft) - 빠진 기능을 조용히 숨기지 않는다 | 12·13 |

**그 아래 - "AI 비서인데 왜 LLM이 없는가"** (출처 `resume/finallq_20260908.md`)

- **결정 공간이 닫혀 있었다** - 도구 20종이 유한하고 확정돼 있다. 선택지가 닫힌 분류 문제에 LLM을 넣으면
  재현성·설명가능성을 잃는다. `planner`는 키워드 점수로 **최대 3개**를 고르는 규칙 기반
- **금융은 감사 가능성을 요구한다** - 감사 로그에 "모델이 그렇게 판단했습니다"라고 적을 수 없다
- **대신 가드레일 4종에 공을 들였다** - ① 역할 기반 도구 가시성(권한 밖 도구는 **플래너에 도달조차 못 한다**)
  ② `side_effect` 도구 자동 실행 금지 ③ FDS 필수 게이트 ④ 출력 화이트리스트
- **AI는 규칙이 안 되는 곳에만** - IsolationForest(이상거래) · TF-IDF+LogReg(스미싱) · Redis 개인 기준선
- **전환 기준을 미리 정해뒀다** - 매칭 실패율 실측 / 도구 20종 초과 시. 단 **가드레일 4종은 유지**한다
- 정직 표기: **FDS 필수 게이트는 구현돼 있으나 현재 미발동** (`_TRANSFER_TOOL_NAMES`가 빈 집합 -
  오케스트레이터에 송금 툴이 아직 없다. 코드 주석·백로그 Pool 90에 기록)
- 계측: LLM·외부 AI API 호출 **0건**(전수 grep) · 툴 **20종** · 백엔드 테스트 **1,098건** · AI 엔드포인트 **12개**
- A2A: 수신 **7스킬**. `assess-loan`이 InsuQ `verify-collateral-insurance`를 **2차 홉으로 실제 호출**

> ⚠️ 기간 표기: FinAllQ는 **2025.10.27~** (Q 시리즈 중 가장 오래됐다). Sprint 번호는 주 단위로
> 변하므로 카드 본문에 쓰지 않는다 (README 경고 규약).

### C. InsuQ (하위) - RAG 집중 + LangGraph 흐름도

**한 줄**: *"AI가 판정하지 않는다. 근거를 모아 원문 그대로 주고, 판단은 사람이 한다."*

**설계사 관점의 검색** (사용자 설명 + 코드 실측)
- 고객이 가입한 상품으로 **먼저 좁혀 찾는다** (`product_filter`)
- 조문이 다른 조문을 참조하면 **그 `refs`를 따라 재검색** - 멀티홉.
  같은 약관 파트 안에서만, 깊이 제한(`resolve_max_hop_depth`, 하드 상한 clamp)

**LangGraph 노드 흐름도 - 카드 본문에 인라인 SVG** (모달 아님. InsuQ의 주인공이라 접지 않는다)

실측 소스: `InsuQ/ai-engine/insuq_ai/agent/graph.py`

```
question + provided_slots
        │
   ┌────▼──────────────── StateGraph ──────────────┐
   │  route    분류 - 키워드 fast-path → LLM 폴백 1회 │
   │             SIMPLE_LOOKUP / VERDICT / CLARIFY   │
   │             (COMPARE는 VERDICT로 강등)           │
   │    │                                            │
   │  clarify  route==CLARIFY일 때만 슬롯 검사        │
   │             슬롯 충족 or 기능 off → VERDICT 강등  │
   └────┬───────────────────────────────────────────┘
        │
   CLARIFY ─────▶ 되묻기 질문 (LLM 0회 - 슬롯→문구는 순수 조회)
        │
   그 외 ───────▶ 검색 → 멀티홉(refs) → 생성
                    │
                    ├ 방어선① 근거 한정 프롬프트 · 인용 필수
                    ├ 방어선② 단정 표현·부분 환각 → verdict=HOLD 강등
                    └ route==VERDICT면 decide() 판정 3단계 + 확인 필요 사항
```

> ⚠️ **정확성 주의**: 컴파일된 `StateGraph`의 노드는 `route` · `clarify` **둘뿐**이다.
> 멀티홉·판정은 그래프 노드가 아니라 그 뒤 파이프라인(`answer_question_stream`)에 있다.
> "LangGraph 노드 4개"라고 쓰면 사실이 아니다 - 위 그림처럼 **경계를 나눠** 그린다.

- **"만들고 → 측정하고 → 기법으로 개선"** - 커밋 메시지에 지표를 넣어 git 히스토리가 개선 서사가 되게 했다

## 4. 기술 설계

### 4-1. 하위 드롭다운

기존 `.pcard` 아코디언과 **같은 패턴**을 쓴다 - 테마·언어 전환·인쇄 CSS가 이미 이 패턴을 전제로 돈다.

```html
<article class="subcard">
  <div class="sub-top">…<span class="sub-caret">▶</span></div>
  <div class="sub-body"><div class="sub-inner">…</div></div>
</article>
```

- 토글: `.sub-top` 클릭 → `.subcard.open`. **`stopPropagation`** 으로 부모 `.pcard`가 닫히지 않게 한다
- `.pcard.open .pc-body { max-height: 1400px }`가 중첩을 자른다 →
  `:has(.subcard)`인 카드만 상한을 올린다. 이 파일은 이미 `:has()`를 쓰고 있다(`.pc-grid:has(.pc-figure.wide)`)

### 4-2. 모달

```html
<button class="feat" data-modal="f-maintq-repeat">반복 고장 감지 → 발주 보류</button>
…
<div id="fmodal" hidden>
  <div class="fmodal-card" role="dialog" aria-modal="true">
    <button class="fmodal-x">✕</button>
    <div class="fmodal-body">
      <section id="f-maintq-repeat" hidden>
        [인라인 SVG 다이어그램] / 어떤 기능인가 / 흐름 ①②③④ / <img data-src="…">
      </section>
      …
    </div>
  </div>
</div>
```

**핵심 결정 - 복제하지 않고 `hidden`만 토글한다.**
모달 본문이 처음부터 DOM에 있으므로 기존 `applyLang()`이 그대로 닿는다 →
**모달 안에서도 KO/EN 전환이 동작**한다. `cloneNode`로 복제하면 복제본은 언어 전환을 못 받는다.

- GIF는 `data-src`로 두고 **모달을 열 때만** `src`를 주입 → 초기 로딩 영향 0
- 닫기: ESC · 배경 클릭 · ✕. 포커스 트랩, 열기 전 포커스 복원, `aria-modal="true"`
- 다이어그램은 **인라인 SVG** - 외부 의존 없고 `currentColor`로 라이트/다크 양쪽 대응

### 4-3. 인쇄

- `.sub-body` · `.sub-inner`를 펼침 목록에 추가, `.sub-caret` 숨김
- `#fmodal`은 `display:none` (모달은 인쇄 대상 아님). 기능 **목록**은 남는다
- `print/index.html`은 중첩 없이 **전부 펼친 형태**로 같은 사실을 싣는다

### 4-4. 언어

모든 문구는 `data-ko` / `data-en` **두 속성 + 태그 안쪽 내용** 3곳을 함께 쓴다 (README 규약).

### 4-5. 기준일

```js
const AS_OF = { y: 2026, m: 9, d: 11 };
```

이 한 줄이 히어로 배지(`.as-of`)와 프로젝트 섹션(`.sec-asof`)을 함께 렌더한다.
소스 문서 기준일: QMesh 09-08 · InsuQ 09-09 · SpendQ 09-10 · MaintQ 09-11 - 전부 09-11 이하라 모순 없다.
