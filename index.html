A2A 멀티 에이전트 오케스트레이션 허브

QMesh ★ AI AGENT 대표작

2026.08 · 개인 1인 · 프로토콜 설계·오케스트레이터 전담
#A2A#MultiAgent#ProtocolDesign#HumanInTheLoop
▶
◆ 해결한 문제

스택도 소유권도 다른 세 도메인 에이전트(금융·보험·제조)를 잇는 문제. MCP는 자기 도구를 쓰는 층이라, 남의 조직 에이전트에게 일을 맡길 때 필요한 신원 증명·사람 승인 대기·크로스도메인 추적을 다루지 못한다.

◆ 설계 포인트
  • 중립 프로토콜 계층: 연결 코드를 어느 도메인에도 종속시키지 않고 별도 레포로 분리. Agent Card 3종 + Task JSON Schema 13종을 SSOT로 고정.
  • Actor / Subject 신원 분리: 인증(누가 부르나)과 인가(누구 데이터인가)를 나누고, 위험도별 3단 자격증명 스코프(조회·심사·자금이동)를 적용.
  • HITL 2단 승인: 자금이동은 요청 부서 → 집행 부서 재무 승인. AI는 초안까지만 쓴다 — 프롬프트가 아니라 도구 권한 수준에서 강제.
  • request_chain_id 분산 트레이스: MaintQ → FinAllQ → InsuQ 멀티홉 여정 하나를 단일 타임라인으로 묶어 감사 로그에 남긴다.
◆ 연결 대상 — 직접 만든 Q 시리즈
  • FinAllQ · 은행·증권 통합 금융 비서 — Spring Boot 3 + FastAPI + React 19 하이브리드 MSA, A2A 수신 어댑터·FDS·감사 로그 운영 :9001
  • InsuQ · 실손 약관 RAG 에이전트 — Qdrant + Nemotron 임베딩, 근거 조항과 함께 답한다. 골든셋 Hit@5 실측 0.81(실손)·0.63(화재·기업성) — 격차 원인 규명 중 :9002
  • MaintQ · 제조 설비보전 에이전트 — MCP 도구 20종(코어 7 + 확장 13) 오케스트레이션, Postgres 전환 완료 :9003
  • 세 프로젝트 모두 언어·프레임워크·저장소가 서로 다르다 — 그래서 연결에 표준 계약이 필요했다.

키지기 · 개인 개발자용 자격증명 관리 도구

KEYLENS

2026.06 ~ 진행 중 · 개인 1인 · 기획·개발·배포 전 과정
#LocalFirst#AES-256-GCM#OCR분류#OpenSource
▶
◆ 해결한 문제

API 키·토큰·ID가 메모장에 흩어진다. 노션의 database_id·data_source_id·page_id는 전부 같은 32자리 UUID라 값만 봐서는 구분이 안 되고, 정규식 기반 시크릿 스캐너는 정확히 이 지점에서 "여러 후보 가능"이라며 손을 든다.

◆ 설계 포인트
  • 값이 아니라 맥락으로 분류: 접두사가 분명한 키(sk-·ghp_·AKIA)는 정규식으로 즉시 판별하고, 애매한 키는 OCR로 읽은 주변 라벨과 URL 구조로 가린다. 신호가 충돌하면 단정하지 않고 "확인 필요"로 남긴다.
  • 로컬 우선(local-first): 내가 운영하는 서버가 없다. 마스터 비밀번호에서 Argon2id로 유도한 키로 AES-256-GCM 암호화해 SQLite에 암호문만 저장하고, 외부로 나가는 기능은 전부 사용자가 직접 켜야 하는 옵트인이다.
  • 삭제까지 책임진다: SQLite 기본 DELETE는 VACUUM 전까지 디스크에 포렌식 복구가 가능하게 남는다 — PRAGMA secure_delete + VACUUM으로 그 잔여까지 지운다.
  • YAML 한 장으로 서비스 확장: 키 종류·라벨·URL 패턴·환경변수명·검증 엔드포인트를 YAML로 선언 → 파일 하나만 추가하면 백엔드·프론트 양쪽에 자동 반영된다(현재 10종).

에이전트 자율 조달 · 역경매 + 조건부 정산

SPENDQ

2026.08 · 개인 1인 · 개인 설계 프로젝트 · 프로토타입
#x402#A2A#Solana#Escrow
▶
◆ 문제 정의

x402는 에이전트 결제의 사실상 표준이 됐지만 일방적이다. 판매자가 가격을 정하고 구매자는 내거나 만다 — 협상도, 경쟁 입찰도, 결제 후 결과가 나빴을 때 되돌릴 방법도 없다.

◆ 설계 포인트
  • 역경매: 하나의 필요를 브로드캐스트하면 판매자 에이전트들이 각자 HTTP 402로 응찰하고(가격·리드타임 상이), 정책 엔진이 낙찰한다.
  • 조건부 정산(에스크로): 결제금을 온체인에 잠그고 인도물 검증을 통과해야 release — 실패하면 자동 환불하고 차순위로 재낙찰한다.
  • 판단은 LLM, 강제는 체인: 지출 한도를 프롬프트가 아니라 온체인 계정에 둔다. 모델이 환각해도 한도를 넘는 트랜잭션은 체인이 거부한다.
  • 호환이 아니라 확장: 402 협상 봉투는 표준 그대로 두고 정산 스킴만 얹었으며, accepts에 표준 exact를 함께 실어 미지원 상대와도 거래된다.
