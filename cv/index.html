★SELF-INTRODUCTION

Agent끼리 소통하게 한다면?

금융·보험·제조 세 분야를 각각 다른 회사로 가정해 에이전트를 만든 뒤, 이들이 서로 일을 주고받게 하는 A2A 연결 계층(QMesh)을 만들었습니다. 예를 들어 공장이 중고 설비를 담보로 대출을 요청하면, 은행이 담보 가치를 평가하다 그 설비의 화재보험이 유효한지 보험사에 다시 조회합니다. 모인 근거는 심사자에게 보여 주고, 승인은 사람이 합니다. 언어도 저장소도 다른 세 시스템은 서로의 코드를 붙이지 않고 계약만으로 이었습니다. 각 에이전트가 할 수 있는 일을 적은 소개서(Agent Card)와 요청 양식 13종을 어느 서비스에도 속하지 않는 한 곳에서만 관리하고, 약속에 없는 값이 오면 조용히 넘기지 않고 오류로 알리게 했습니다. 까다로웠던 것은 신원 확인이었습니다. 요청을 보낸 쪽과 그 요청이 다루는 자료의 주인을 나눠 확인하고 나서야 조회·심사·자금 이동 순으로 권한을 좁힐 수 있었습니다.

에이전트 하나에도 권한을 나눠서

AI 코드 보안 분석 플랫폼(SecureAI Engine)에서는 개인 개발자·팀·기업 보안 조직으로 사용자층을 나눠 계정 권한별로 기능을 분리하고, AI 엔진은 데이터베이스에 직접 닿지 못하게 해 권한 확인이 백엔드 한곳에서 이뤄지게 했습니다. 설비 보전 에이전트(MaintQ)에서는 데이터를 쓰는 도구가 초안만 만들게 해 승인은 사람이 하고, 요청자 신원은 서버가 직접 넣어 AI가 신원을 꾸밀 수 없게 했습니다.

현업에서는 먼저 배우겠습니다

개인 프로젝트에서는 제가 가정한 회사와 사용자를 기준으로 권한을 나눴지만, 실제 현업의 권한 체계는 규모도 무게도 다를 것이라 생각합니다. 함께하게 되면 기존 구조와 업무를 먼저 배우고, 맡은 기능에는 권한 범위를 지키는지 확인하기 위해 테스트를 꼼꼼히 하겠습니다. 설계할 때 가장 즐겁게 일하는 만큼, 현장의 시스템을 직접 만들며 익혀 언젠가는 전체 구조를 설계하는 아키텍트가 되고 싶습니다.
