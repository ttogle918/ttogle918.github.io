KOCRUIT는 서류 평가부터 AI 면접 · 대면 면접 · 리포트까지 채용 전 과정을 돕는 플랫폼입니다. AI는 합격 · 불합격을 정하지 않고 근거만 제시하며, 최종 판단은 사람이 합니다. 팀 프로젝트로 만든 이 플랫폼을 혼자 이어받아, 서비스 경계와 검증 체계부터 다시 세우고 있습니다.

아키텍처

상태는 backend, 분석은 무상태 서비스

재설계 조사의 결론은 «컨테이너를 나눈 것이 문제가 아니라, 나누면서 계약을 정하지 않은 것이 문제»였습니다. 그래서 경계는 유지하고, 경계를 넘는 방식을 바꿨습니다.

① 경로 금지

파일 경로를 주고받지 않습니다

배치 입력은 MediaObjectRef(버킷 · object_key)로만 받습니다. stt-service에는 경로 입력 자체가 없습니다.

② 클라이언트 경유

서비스 주소는 한곳에만 둡니다

서비스 URL 문자열이 clients/와 설정 밖에 생기면 정적 테스트가 실패합니다. 처음 세어 보니 18곳이었고, 지금은 0건입니다.

③ 스키마 공유

경계마다 같은 스키마를 씁니다

Pydantic 정의를 shared/kocruit_schemas 한 곳에 두고, 각 서비스가 같은 패키지를 설치해 씁니다.

서비스 하는 일 하지 않는 일
backend 상태 · 세션 · DB · 인증 · 미디어 업로드 AI · 미디어 라이브러리, 오디오 디코딩
stt-service 디코딩 · 전사 · 화자 라벨 LLM, DB, 세션 상태
agent LangGraph · LLM · 질문 생성 · RAG · 챗봇 오디오, WebSocket, 세션 상태
video-analysis 영상에서 표정 · 시선 · 자세 지표 음성, LLM
어디에 집중했나

시간을 가장 많이 쓴 다섯 가지

기능 목록보다 이쪽이 이 리팩토링의 핵심입니다.

①LLM 호출 하나가 서버 전체를 멈추고 있었습니다

agent 엔드포인트 60개가 전부 async def였는데 안에서는 동기 .invoke()를 부르고 있었습니다. FastAPI에서 async def 핸들러는 이벤트 루프에서 직접 돌기 때문에, LLM 18.1초 요청 동안 헬스체크가 17.05초 걸렸습니다. 핸들러 35개를 def로 되돌려 스레드풀로 보냈고, 그 뒤에는 LLM 43초 요청 중에도 헬스체크가 최대 0.02초였습니다.

핸들러 안의 느린 것 처분
다른 서비스 HTTP 호출 진짜 비동기로 - httpx.AsyncClient, clients/ 경유
동기 DB 세션 (밀리초 급) 이벤트 루프에서 수용 - 비동기 ORM 전면 전환은 별도 항목으로 등록하고 스테이지마다 다시 논의하지 않습니다
CPU · 모델 추론 스레드로 감싸지 않고 해당 서비스로 이관
본문에 await가 없음 def로 환원 - DB 작업까지 루프에서 빠집니다

규칙은 문서에만 적으면 다음 스테이지에서 뒤집힙니다. 그래서 async def 라우트 본문의 동기 호출을 AST로 찾는 스캐너를 만들고, 기존 위반 7건을 허용 목록에 넣은 뒤 0건까지 줄였습니다. 스캐너 자체도 의심했습니다. 위반을 하나 지우면 «허용 목록이 낡았다»로 실패하는지, 문법 오류 파일에서 조용히 통과하지 않는지 확인했고, 같은 파일 안에서 위치만 바뀌면 개수 비교로는 못 잡는다는 한계를 테스트로 적어 두었습니다.

②경계를 객체 참조로 바꾸고, 전사를 별도 서비스로 뺐습니다

음성 업로드는 backend가 자기 /tmp에 파일을 쓰고 그 경로를 agent에 넘기는 구조였습니다. 공유 볼륨은 agent와 video-analysis에만 붙어 있어서 agent는 항상 «audio not found»로 실패했습니다. MinIO를 도입해 서비스 사이에는 MediaObjectRef만 오가게 했습니다.

새 서비스를 설계할 때 먼저 소비자를 셌습니다. agent의 음성 경로 7개 중 실제로 화면이 부르는 것은 1개였습니다. 그래서 «6기능 이관»이던 설계 문서의 완료 기준을 «1개 이관 + 6개 삭제»로 정정했습니다. 쓰지 않는 경로를 새 서비스에 옮겨 심는 것은 빈 코드를 늘리는 일이기 때문입니다.

결정 기각한 쪽의 비용
전사 엔진을 faster-whisper(CPU int8)로 openai-whisper를 그대로 옮기면 빌드용 버전 고정이 새 서비스로 이사만 가고 torch도 따라옵니다
화자분리는 실제로 동작하던 볼륨 기반 방식만 이관 pyannote는 조사 시점에 모델 동의 절차가 안 돼 이미 동작하지 않고 있었습니다. 정밀 분리는 다음 단계로 미뤘습니다
전환 커밋 → 수동 확인 → 삭제 커밋 플래그로 두 경로를 오가게 만들면 곧 지울 분기를 짜야 합니다. 되돌리기는 커밋 revert가 더 쌉니다

결과적으로 agent의 main.py가 1,905줄에서 743줄로, OpenAPI 경로가 60개에서 36개로 줄었습니다. whisper가 빠지자 고정 핀 없이 빌드가 227초에 끝났고 이미지는 3.6GB에서 2.15GB가 됐습니다. 한계도 같이 쟀습니다. 166초 wav 업로드는 화면에서 완료까지 272초가 걸렸고, 프론트 요청 타임아웃이 300초라 여유가 28초뿐입니다. 약 3분이 넘는 녹음은 서버가 성공해도 화면은 실패하므로, 이 숫자를 결함으로 등록해 두었습니다.

③거짓 녹색을 걷어냈습니다

스모크 테스트는 원래 7개 통과 · 2개 실패였는데, 통과도 실패도 둘 다 거짓이었습니다. 통과 하나는 개발기의 호스트 8002 포트를 쓰던 다른 프로젝트의 컨테이너를 보고 나온 녹색이었고, 실패 둘은 포트 재매핑 때문이었을 뿐 서비스는 살아 있었습니다.

서비스 헬스를 docker exec 컨테이너 내부 확인으로 바꿔 호스트 포트와 무관하게 만들었습니다. docker가 없거나 컨테이너 이름이 틀리면 SKIP(판단 불가), 컨테이너가 멈췄으면 FAIL로 나누고 종료 코드를 0 · 1 · 2로 구분해, SKIP이 조용한 성공으로 보이지 않게 했습니다.

두 번째 부류는 «쓰기 성공만 보고 완료로 판정한 검증»이었습니다. 서류 평가 수정의 완료 조건은 «DB에 합격이 기록된다»였는데, 그 행을 읽는 지원자 목록 화면은 500이었습니다. 없는 영상 결과가 404를 돌려주게 고쳤더니, 그 응답을 읽는 화면은 애초에 엉뚱한 API를 부르고 있었습니다. 둘 다 자동 테스트가 아니라 브라우저 수동 확인에서만 잡혔습니다. 그래서 다음 스프린트부터 모든 항목의 완료 조건을 자동 테스트 / 실측(어느 컨테이너를 보는지 명시) / 그 데이터를 읽는 화면 확인 세 칸으로 나눴습니다.

④보안 결함은 수동 확인 중에 나왔습니다

계정을 A에서 B로 바꾼 직후 B의 토큰으로 내 정보를 조회했는데 A의 정보가 돌아왔습니다. 고친 것과 못 고친 것을 나눠 적습니다.

결함 처분 상태
캐시 미들웨어가 인증된 GET 응답 전부에 Cache-Control: public을 붙여, 같은 브라우저에서는 토큰이 달라도 캐시를 재사용했습니다 2xx는 private + Vary: Authorization, 오류 · 인증 경로는 no-store. 지원서 · 이력서 · 전사 경로는 한 단계 더 낮췄습니다 해소
음성 분석 POST 3개에 인증이 없었고, «운영 전 비활성 필요»라고 주석만 달린 개발용 공개 라우트가 항상 열려 있었습니다 회사 사용자 인증과 지원서 회사 일치 검사(403)를 붙이고 공개 라우트를 삭제했습니다. object_key의 지원서 번호까지 이중으로 검증합니다 해소
지원자 목록 API가 다른 회사 토큰에도 200을 돌려줬습니다. 수동 확인 중 실제 브라우저에서 타 회사 지원자 목록 화면까지 들어갔습니다 하나씩 고치지 않고 같은 부류를 전수 조사해 한 번에 닫았습니다. 두 스테이지에 걸쳐 55개 라우트에 회사 스코프를 부여했습니다 해소 (2026-09-16)
영상 유무(404)를 회사 검사(403)보다 먼저 판정해, 응답 코드로 타 회사 지원서의 영상 존재를 알 수 있었습니다 코드 리뷰 게이트가 발견해 같은 보안 묶음에 등록했습니다 등록
개발용 로그인 경로에 가드가 없어 모든 빌드에서 이메일만으로 토큰을 받을 수 있었습니다 환경 플래그(기본 꺼짐)로 경로를 404로 숨기고, 버튼은 개발 서버에서만 나오게 했습니다. 이메일을 찍던 로그도 지웠습니다 해소

고친 것보다 중요한 건 다시 늘지 않게 만든 것입니다. 런타임 app.routes를 읽어 인증 · 회사 스코프가 없는 라우트를 허용목록과 대조하는 인가 래칫을 테스트로 두었습니다. 목록에 없는 무인증 라우트가 새로 생기면 실패하고, 이미 고친 항목이 목록에 남아 있어도 실패합니다. 무인증 라우트는 143개에서 98개가 됐습니다.

⑤에이전트에게 역할을 나눠 맡기고, 결정과 커밋 게이트는 넘기지 않았습니다

Claude Code의 서브에이전트를 역할별로 정의해 스프린트를 운영했습니다. PM은 쟁점마다 권고안과 기각안의 비용을 내고, Dev 평가는 계획의 줄번호 · 개수 주장을 다시 재서 진행 여부를 말하고, Tester는 완료 조건 세 칸을 검증하고, Reviewer는 보안 · 경계 위반이 있으면 커밋을 막습니다. 결정은 제가 합니다. 스프린트 3에서만 9건을 직접 결정했습니다.

서류 평가 버그는 상태 스키마에 키 한 줄 추가 값을 버리는 지점이 둘이었습니다. 계획대로면 정적 테스트는 녹색이 되고 버그는 남습니다
하드코딩된 서비스 주소 4건 clients/ 밖에서 18건
병렬로 돌린 작업끼리 파일 충돌 없음 파일은 안 겹쳤지만 같은 컨테이너의 자동 재시작을 공유해 서로의 실호출을 끊었습니다. 계획 표에 «환경 자원» 열을 추가했습니다
리뷰어의 수치 정정 권고 리뷰어의 검색 범위가 핵심 파일을 빠뜨린 것이었습니다. 검증 없이 받았으면 맞는 숫자를 틀리게 바꿨을 것입니다

에이전트에게 일을 맡기는 것은 확인을 줄이는 일이 아니라, 확인할 지점을 미리 정해 두는 일이었습니다. 제가 하위 에이전트에게 넘긴 작업 지시서의 실측값이 세 번 틀렸고, 세 번 모두 에이전트 쪽이 컨테이너 확인과 원본 대조로 잡아냈습니다. 그래서 지시서의 실측값도 틀린다는 전제로, 하위 에이전트에게 실측으로 지시를 정정할 권한을 명시했습니다.

정확도

화자분리는 아직 볼륨 기반입니다

현재는 소리 크기로 화자를 나눕니다. pyannote 정밀 분리는 배치 복구 단계에서 붙입니다. 긴 녹음도 한계가 있어, 약 3분이 넘으면 서버는 성공해도 화면은 타임아웃으로 실패합니다(여유 28초).

경계 계약 테스트 2건은 알려진 결함이라 빨강 그대로 둡니다(필기 채점 500, 면접 준비 라우트 주석 처리). 캐시는 키가 객체의 메모리 주소에 의존해 요청마다 달라집니다. 80요청에 고유 키 82개 · 적중 0회로 실측해 등록했습니다.
