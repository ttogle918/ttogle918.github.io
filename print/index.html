문제

연결 대상 ① FinAllQ - 은행 · 증권 통합 금융 비서

2025.10~ · Spring Boot 3 + FastAPI + React 19 하이브리드 MSA. 기능은 통합 대시보드 · 여신 심사 근거 카드 · 여신 ↔ 이체 연결 · 기업 이체 결재(직무 분리) · FDS 고위험 → 2FA 승격 · 스미싱 탐지 · AI 비서 Fail-soft.

해결 방법 'AI 비서'라는 이름이지만 LLM 대신 규칙 기반을 택했습니다. 사용할 기능이 20가지로 정해져 있었고, 금융에서는 판정 근거를 감사 기록으로 남길 수 있어야 했기 때문입니다. 대신 이상거래와 스미싱처럼 규칙으로 다 적을 수 없는 곳에는 실제로 모델을 썼습니다. 코드 전체를 검색해 생성형 AI 호출이 0건인 것을 확인했고, 서버 테스트 1,254건이 모두 통과합니다. 상세 ttogle918.github.io/#finallq

연결 대상 ② InsuQ - 보험 약관 분석 · 보장 판정 RAG

2026.07~ · Spring Boot 4 + FastAPI/LangGraph + Qdrant + Next.js. 기능은 근거 인용 · 거부 게이트 · 되묻기 · 청구 승인(사람 앞에서 멈춘다).

해결 방법 AI가 틀렸을 때도 설계사가 근거를 보고 판단할 수 있어야 한다고 봤습니다. 그래서 가입한 상품 안에서만 찾고, 답에는 근거 조항을 원문 그대로 붙였습니다. 결론은 가능성 높음 · 낮음 · 판단 보류로만 내고, 단정하는 표현이 나오면 판단 보류로 바꿔 내보냅니다. 질문 27개로 채점해 정답 조항이 상위 5개에 든 비율 0.81, 답할 수 있는 질문을 거절한 경우 0건. 실험 67건은 기각한 시도까지 기록했습니다. 화재보험 평가 수치와 아직 재지 못한 부분(AI 채점 공란)은 상세 페이지에 함께 적었습니다. 상세 ttogle918.github.io/#insuq

연결 대상 ③ MaintQ - 제조 설비 진단 · 부품 발주

2026.07~ · Python FastAPI + MCP + PostgreSQL(pgvector) + Next.js. 기능은 미지 에러코드 처리 · 재고 0 → 호환 대체품 · 반복 고장 감지 → 발주 보류 · 처분 사전판정 · 처분 근거 번들 · 법정 기한 · 위험등급 · 지출 성격 분류.

해결 방법 두 모델의 부품 특정 정확도가 45.6%와 51.0%로 비슷해서 차이가 없다고 넘길 뻔했습니다. 안을 열어 보니 한쪽은 틀린 부품을 자신 있게 골랐고, 다른 쪽은 답을 내지 않았습니다. 두 실수를 따로 세고, 지시문만 바꾼 비교 실험(각 120회)에서 위험한 쪽을 16.7%에서 1.1%로 줄였습니다. 모르는 에러코드를 지어낸 비율(환각) 0%, 권한 없는 요청 차단 100%. 상세 ttogle918.github.io/#maintq

구현한 시나리오

예를 들어 한 공장에서 설비가 고장 나면, 공장의 정비 AI(MaintQ)가 보험사 AI(InsuQ)에 물어 관련 약관 조항을 근거와 함께 받아 옵니다. 교체 부품을 발주하면 대금 출금 요청이 은행(FinAllQ) 결재함에 도착합니다. 출금은 공장 팀장 · 공장 재무팀 · 은행 결재까지 사람이 세 번 승인해야 이뤄지도록 설계했습니다. 쓰던 설비를 담보로 대출을 신청하면 은행 AI가 다시 보험사 AI에 담보 보험을 확인하고, 감정가를 매겨 판정을 돌려줍니다. 설비를 처분할 때는 은행과 정산해 처분 제한을 풀고 보험사에 처분 사실을 알리지만, 최종 서명은 여전히 사람이 합니다. 이 이야기에 나오는 연결 7가지를 하나씩 목킹 없이 실제 시스템끼리 끝까지 돌려 확인했습니다.

해결 방법
  • 어느 편에도 속하지 않는 연결 계층 - 연결 코드를 어느 한 서비스 안에 넣지 않고 따로 떼어 냈습니다. AI 소개서(Agent Card) 3종과 요청 양식(Task 스키마) 13종을 이 한곳에서만 관리합니다.
  • 가장 오래 헤맨 부분은 신원 확인이었습니다. 요청을 보낸 회사가 누구인지와 그 요청이 누구의 자료를 다루는지를 나눠 확인하게 하고 나서야 풀렸고, 조회 · 심사 · 돈 이동 순으로 허락 범위를 좁히도록 설계했습니다.
  • 출금은 공장 팀장, 공장 재무팀, 은행 결재까지 사람이 세 번 승인합니다. AI는 초안까지만 쓰고, 승인할 권한 자체가 없습니다.
  • 다른 요청은 되는데 보험사까지 한 번 더 거치는 요청만 실패했습니다. 그 구간을 보니 FinAllQ와 InsuQ가 서로 다른 인증 토큰을 쓰고 있었고, 맞춘 뒤에는 옛 토큰을 일부러 다시 넣어 같은 오류가 나는지 확인했습니다.
  • 요청 하나를 끝까지 추적 - 제조 → 금융 → 보험으로 이어지는 요청에 같은 번호(request_chain_id)를 붙여 세 회사의 기록을 하나의 타임라인으로 묶어 남깁니다.

AI 기반 코드 보안 분석 플랫폼
문제

팀 프로젝트에서 AI로 코드를 쓰다 보니 팀원이 .env 파일을 깃에 올리고, API 키가 코드에 그대로 박히는 일이 반복됐습니다. AI가 쓴 코드를 그대로 믿으면 안 되겠다고 생각해 보안 분석 도구를 만들기 시작했습니다.

해결 방법
  • 처음 분석에서는 안전한 React 화면 코드를 XSS 취약점으로, 테스트용 가짜 데이터를 '심각'으로 잡는 일이 많았습니다. 유형별로 나눠 보니 원인이 달라서 프레임워크 규칙을 알려 주고, 테스트 파일은 미리 빼고, 코드 품질 문제는 따로 분류했습니다.
  • 실제로 공격해 보고 확인 - 찾은 취약점을 격리된 실험 환경에서 실제로 공격해 보고, 정말 뚫리는지로 증명합니다. “찾았다”에서 “증명했다”로 바꾼 부분입니다.
  • 5단계 자동 분석 흐름(LangGraph) - 코드 읽기 → 이전 결과 재사용 확인 → Claude로 분석 → 취약점 분류 → 수정 코드 만들기. 중간에 멈춰도 이어서 할 수 있고, 분석 · 수정 · 증거 남기기를 도구로 나눠 AI가 필요할 때 부릅니다.
  • AI가 DB를 바로 조회하게 한다면 편했을 것입니다. 하지만 그렇게 하면 SQL 인젝션을 막는 파라미터 바인딩을 쓸 수 없었습니다. 실제 고객 데이터를 다룬다고 가정하고, 조금 돌아가더라도 서버 API를 거치게 바꿔 DB에 접근할 수 있는 경로를 줄였습니다(ADR-016).
설계에서 신경 쓴 것
  • AI 여럿에게 역할을 나눠 맡겼습니다 - 총괄 · 기획 · 개발 · 리뷰 · 문서 역할의 Claude Code 에이전트를 동시에 돌려, 혼자서 Sprint 0~30(커밋 880개)을 끝까지 진행했습니다.
  • 실제 운영에 필요한 것까지 붙였습니다 - 서비스 상태 모니터링(Prometheus · Grafana · Jaeger), 분석 진행 상황 실시간 전송(SSE + Redis), 4겹 네트워크 분리, 로그인 토큰 안전 보관(JWT HttpOnly).
  • 쓰는 곳을 넓혔습니다 - 코드 편집기(VSCode) 확장에서는 코드 바로 옆에 취약점을 표시하고, 안드로이드 앱까지 같은 서버에 연결했습니다.
결과 - 탐지율은 올렸고, 오탐은 과제로 남음

문제

보조강사로 일하며 수강생들이 API 키를 코드에 그대로 두는 걸 자주 봤고, 시중 도구보다 단순하게 키를 보관할 방법이 필요하다고 생각했습니다. 막힌 곳은 노션의 여러 ID처럼 모양이 똑같은 값이었습니다. 값만 봐서는 무슨 키인지 알 수 없었습니다.

해결 방법
  • 값이 아니라 주변 맥락으로 분류 - 앞부분만 봐도 알 수 있는 키(sk- · ghp_ · AKIA)는 바로 판별하고, 애매한 값은 화면 캡처에서 글자를 읽어(OCR) 옆에 적힌 이름표와 주소 구조로 구분합니다. 단서가 엇갈리면 단정하지 않고 “확인 필요”로 남깁니다.
